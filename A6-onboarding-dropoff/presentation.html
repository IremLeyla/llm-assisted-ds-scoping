Scenario A6

User Onboarding Drop-off

Scoping the problem before building any model.

~10 s. "Hi, I'm Irem. I'll present two scenarios, and both follow one idea: before using AI, find out what the data can honestly tell us, and what it can't. First, A6, onboarding drop-off."
1 · The problem

"Users abandon onboarding."

  • No agreed definition of abandonment
  • No labels, only raw event logs
  • No explanation of where or why
We don't know where users disengage or which patterns come before it. The onboarding product team will use the answer to decide which steps to redesign or test first.
~30 s. "Users abandon onboarding, but nobody has defined 'abandon', and there are no labels, only event logs. So defining it is part of the problem. My working definition: the user started, didn't reach the final step, and didn't come back within a few days. I first assumed everyone drops off on one page, like the third. Now that's a hypothesis for the data to test. The people who will use our results are the team that owns the onboarding flow. They need to know which screen to improve first."
2 · Framing

Diagnose first, predict later

Unsupervised learning Representation learning
  • No labels, so we first discover the structure: which paths exist
  • A classifier would learn our guess of "abandonment" and say who leaves, not where
  • Later: A/B tests to check that fixes work
~30 s. "My first idea was recommendation and A/B tests. I learned that list names the type of ML problem. With no labels, it's unsupervised learning, with representation learning for the event data. A classifier would only learn our guess of abandonment, and tell us who leaves, not where. A/B tests come later."
3 · Data

What we have, and what could mislead us

  • Event logs (taps, scrolls, screen views) plus install and device info
  • Kept at event level, not one row per user, so the order of events survives
  • No labels. The reminder-email rule could be a first weak label
  • Risks: users who haven't returned yet, install-only users with no events, privacy (GDPR)
~25 s. "What data would we have? Event logs: taps, scrolls, screen views, plus install and device information. I learned to keep the data at event level, not one row per user, because otherwise we lose the order of events. There are no labels, but an existing reminder-email rule could be a first weak label. The risks: users who haven't had time to return, install-only users who produce no events at all, and privacy."
4 · Approach

Event logs in, user paths out

Sequence clusteringGroup users by the path they take. Finds archetypes like "leaves after screen one".
Process miningMap real transitions between screens. Shows what a simple funnel hides.
Survival analysisTime until drop-off. Handles users who haven't left yet.
~20 s. "Three approaches: sequence clustering finds the user groups, process mining maps the real paths between screens, and survival analysis models timing."
5 · The "why"

Logs show behaviour, not motivation

  • Where and how users leave: event data and our models
  • Why they leave:
User interviews Exit surveys Session replays A/B tests

No labels, so we judge clusters by stability, comparison with the reminder-email rule, and product-team review.

~20 s. "Where and how users leave comes from the event data. For the why, we'd add interviews, exit surveys, session replays and A/B tests. And with no labels, we'd judge the clusters by their stability, by comparing them with the reminder rule, and by product-team review."
6 · What I learned

Survival analysis

300 of 1,000 new users haven't finished onboarding, but 200 installed yesterday and may finish tomorrow. Only about 100 have really dropped off. Survival analysis keeps those "not yet" users in the data instead of counting them as failures.
  • Corrected assumption: drop-off at one page is a hypothesis, so let the data show where
  • LLM used as a thinking partner, I made the final calls
~25 s. "My new method is survival analysis. Of 1,000 new users, 300 haven't finished onboarding. But 200 installed yesterday and may finish tomorrow, so only about 100 have really dropped off. Survival analysis keeps those 'not yet' users in the data instead of counting them as failures."
7 · How I used the LLM

Thinking partner, my decisions

  • It helped: showed that "abandonment" has several possible definitions, so defining it is part of the problem
  • I added: the reminder-email observation and example user groups, which refined the data scope
  • It corrected me: I read the problem-type list as "what to recommend". It names the kind of ML problem
~20 s. "I used the LLM as a thinking partner: it drafted and explained, and I decided. It helped me see that 'abandonment' has several possible definitions. I added the reminder-email observation and the example user groups, which refined the data scope. And it corrected me: I read the problem-type list as 'what to recommend', but it names the kind of ML problem."
