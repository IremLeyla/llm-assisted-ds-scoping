Scenario A6

User Onboarding Drop-off

Scoping the problem before building any model.

~10 s. Intro: product manager scoping with a DS team; the goal is to define the problem, not to build a model.
1 · The problem

"Users abandon onboarding."

  • No agreed definition of abandonment
  • No labels, only raw event logs
  • No explanation of where or why
We don't know where users disengage or which patterns come before it. The onboarding product team will use the answer to decide which steps to redesign or test first.
~35 s. Stress that defining "abandonment" is part of the problem. Working definition: started, did not reach the final step, did not return within X days. "Third page" is a hypothesis, not an assumption.
2 · Framing

Diagnose first, predict later

Unsupervised learning Representation learning
  • No labels, so we first discover the structure: which paths exist
  • A classifier would learn our guess of "abandonment" and say who leaves, not where
  • Later: A/B tests to check that fixes work
~35 s. My first idea was ranking/recommendation and A/B testing. Learned that the list names the ML problem type, and A/B testing is the later validation phase.
3 · Data and approach

Event logs in, user paths out

Sequence clusteringGroup users by the path they take. Finds archetypes like "leaves after screen one".
Process miningMap real transitions between screens. Shows what a simple funnel hides.
Survival analysisTime until drop-off. Handles users who haven't left yet.

Risks: users who haven't had time to return, install-only users with no events, privacy (GDPR).

~40 s. Event-level data, grouped into sessions and one trajectory per user. Keep one row per user too early and you lose the order of events.
4 · The "why"

Logs show behaviour, not motivation

  • Where and how users leave: event data and our models
  • Why they leave:
User interviews Exit surveys Session replays A/B tests

No labels, so we judge clusters by stability, comparison with the reminder-email rule, and product-team review.

~25 s. Be honest about the limit: our methods cannot tell why. The follow-up evidence does.
5 · What I learned

Survival analysis

300 of 1,000 new users haven't finished onboarding, but 200 installed yesterday and may finish tomorrow. Only about 100 have really dropped off. Survival analysis keeps those "not yet" users in the data instead of counting them as failures.
  • Corrected assumption: drop-off at one page is a hypothesis, so let the data show where
  • LLM used as a thinking partner, I made the final calls
